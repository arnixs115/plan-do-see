# 패스키 관리: 여러 개 등록, 개별 삭제 (과제 8 카드 4)

## 여러 개 등록
- 한 계정에 패스키를 최대 10개 등록할 수 있다(`MAX_PASSKEYS_PER_USER`). 등록 절차는 카드 2와 같다(서버 챌린지 → 브라우저 → 서버 검증).
- 같은 인증기(기기·패스키 관리자)에 같은 계정의 패스키를 두 번 만들 수는 없다. 등록 옵션의 `excludeCredentials` 로 브라우저가 거절한다. **두 번째 패스키는 다른 기기나 다른 패스키 제공자에서 이 화면을 열어 등록한다.**
- credential ID 는 DB 고유 제약(`passkey_credentials_credential_id_key`)으로 중복 저장이 안 되고, 새 패스키는 기존 행을 건드리지 않는다.
- 패스키 이름은 사람이 구분하려는 표시용이다. 이름이 "개인 PC"여도 실제 저장 위치가 그 PC라는 뜻이 아니고, 동기화되는 패스키는 여러 기기에서 쓰일 수 있다.

## 목록 (`GET /api/passkeys`, `/account` 화면)
이름, 등록 일시(DB `created_at`), 마지막 로그인, 구분 번호(credential ID 끝 6글자), 종류(동기화될 수 있음/한 기기에 묶임). 전체 credential ID·공개 키·카운터는 응답에 없다. 로그인한 사용자의 것만 조회한다(조회 조건이 세션의 사용자 id).

## 삭제 (`DELETE /api/passkeys/{passkey_id}`)
- `passkey_id` 는 목록의 행 id 다(credential ID 가 아니다).
- 화면: 삭제 → 이름이 적힌 확인 창 → 삭제 확인.
- 서버: `requireUser` 로 로그인 확인 → DB 함수 `delete_passkey(user_id, passkey_id, allow_last)` 가 **소유자 조건과 함께** 지운다. 남의 패스키와 없는 패스키는 모두 404.
- 지운 credential 은 로그인에서 즉시 쓸 수 없다: 로그인 검증이 매번 DB 에서 credential ID 로 찾고(`findCredentialById`, 없으면 401), 카운터 기록(`record_passkey_authentication`)도 행이 있어야 성공한다. 삭제 전에 발급된 챌린지나 만들어 둔 서명도 삭제 뒤에는 통과하지 못한다.
- 서버에서 지우는 것은 "등록된 credential" 뿐이다. 사용자의 기기·패스키 관리자에 저장된 패스키는 자동으로 지워지지 않는다(화면에 안내). 그 쪽은 직접 지운다.
- 이미 발급된 로그인 세션은 패스키를 지워도 끊기지 않는다(세션은 Supabase Auth 가 관리). 세션을 끊으려면 로그아웃한다.

## 패스키 0개 정책
- **마지막 패스키도 삭제할 수 있다.** 단, 서버가 `?confirm_last=1` 없이는 409(`code: last_passkey`)로 거절하고, 화면은 경고를 보여 준 뒤에만 그 값을 보낸다. 같은 사용자의 패스키를 동시에 지워서 확인 없이 0개가 되는 일은 DB 함수의 행 잠금으로 막는다.
- 이유: 이 서비스의 모든 계정은 이메일/비밀번호로도 로그인할 수 있다(패스키는 로그인한 상태에서만 등록됨). 그래서 0개가 되어도 계정에 들어올 수 있고, 최소 1개를 강제하면 잃어버린 기기의 패스키를 정리하는 일만 어려워진다.
- 0개일 때: 목록에 안내 문구, 패스키 로그인은 불가(401), 이메일/비밀번호 로그인과 `/account` 에서 패스키 재등록이 복구 방법이다.
- **한계:** 이 프로젝트에는 비밀번호 재설정 기능이 없다. 패스키를 모두 지우고 세션도 없고 비밀번호도 모르면 계정에 들어올 방법이 없다. 그래서 화면이 이 점을 경고한다.

## 직접 확인하는 절차 (실제 브라우저·패스키 제공자)
1. 마이그레이션 `db/migrations/20261101100000_add_delete_passkey.sql` 을 SQL Editor 에서 실행하고 재배포한다.
2. 기기 1(예: PC)에서 로그인 → `/account` → 이름 "시험 A" 로 패스키 등록.
3. 기기 2(휴대폰 또는 다른 패스키 제공자)에서 같은 계정으로 로그인 → 이름 "시험 B" 로 등록. (같은 제공자·같은 기기에서는 "이미 있습니다" 안내가 나온다. 제공자가 패스키를 동기화한다면 기기 2에서도 A 가 보일 수 있다.)
4. 목록에 두 개와 각각의 이름·등록 일시·구분 번호가 보이는지 본다. 구분 번호가 서로 다른지 본다.
5. "시험 A" 삭제 → 이름이 적힌 확인 창 → 삭제 확인 → 목록에 "시험 B" 만 남는지 본다.
6. 로그아웃 → 「패스키로 로그인」 → "시험 B" 선택 → `/plans` 로 이동, `/private` 에서 비공개 항목이 보이는지 본다.
7. 다시 로그아웃 → 「패스키로 로그인」. 브라우저가 "시험 A" 를 후보로 보여 주면 선택해 본다: 서버가 거부하고 "패스키로 로그인하지 못했습니다" 가 나와야 한다. 후보로 안 보이면 그 사실을 기록한다(브라우저·제공자마다 다르다).
8. 마지막 패스키 삭제는 시험 계정에서만 해 본다: 경고 문구가 보이는지, 삭제 뒤 비밀번호로 로그인해 `/account` 에서 다시 등록할 수 있는지 본다.
9. SQL Editor 에서 `db/checks/passkey-registration.sql` 의 10·11번을 실행한다(개수만 나오고 키는 나오지 않는다).
10. 스크린샷에 쿠키·토큰이 보이지 않게 한다. 구분 번호는 끝 6글자라 캡처해도 된다.
