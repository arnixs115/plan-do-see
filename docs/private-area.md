# 비공개 영역과 서버 측 접근 제어 (과제 8 카드 1)

로그인한 사람에게만 보이는 비공개 영역과, 그것을 서버가 지키는 방식에 대한 기록입니다.
**확인한 것**과 **확인하지 못한 것**을 구분해 적었습니다.

## 이번 카드의 범위

| 항목 | 상태 |
|---|---|
| 비공개 영역 화면 `/private`, 비공개 API `GET /api/private-items` | 구현함 |
| 서버가 로그인을 확인하고 비로그인 요청에는 항목을 주지 않음 | 구현함 |
| 공개 소개 페이지를 첫 화면으로 두기 (과제 1 내용) | **미구현.** 저장소에 과제 1 소개 내용이 없어서 만들어 채우지 않았다. 원문을 받아야 한다 |
| 패스키 등록·로그인 ("나만 들어가기") | **미구현.** 다음 카드 |

지금의 `/`는 과제 6·7의 계획 대시보드이고 로그인해야 열립니다. 첫 화면이 공개 소개 페이지가 되는 변경은 하지 않았습니다.

## 가상 데이터입니다

비공개 영역의 항목 4개(개인 메모 2, 학습 목표 1, 비공개 프로젝트 계획 1)는 **전부 만들어 낸 가상 데이터**입니다.
실제 사람·계정·연락처·일정과 관계가 없고, 화면에도 "가상 데이터"라고 적혀 있습니다. 화면에는 로그인한 계정의 이메일도 보이지 않게 했습니다.
항목은 DB가 아니라 서버 전용 코드(`lib/private/items.ts`)에 있습니다. 그래서 이 카드에서는 DB를 바꾸지 않았고, 모든 로그인 사용자에게 같은 가상 항목이 보입니다.
실제 비공개 자료를 넣게 된다면 소유자 열과 소유권 검사가 먼저 필요합니다. (`lib/auth/ownership.ts`의 방식 참고)

## 구현 방식

| 파일 | 역할 |
|---|---|
| `lib/private/items.ts` | 가상 항목과 `listPrivateItems(user)`. `import "server-only"`라서 클라이언트 컴포넌트가 가져오면 빌드가 실패한다. 로그인 확인을 마친 사용자 객체를 인자로 받는다 |
| `app/api/private-items/route.ts` | `GET`만 제공. 맨 앞에서 `requireUser()`를 호출해, 로그인하지 않았으면 항목을 읽기 전에 **401**, 인증 서버 장애면 503. 응답은 `no-store`이고 이메일·사용자 id를 담지 않는다 |
| `app/private/page.tsx` | 서버 컴포넌트. `getCurrentUser()`가 없으면 항목을 읽기 전에 `/login`으로 보낸다. 반전된 색 띠와 굵은 점선 테두리로 일반 화면과 구분한다. `noindex` |
| `app/app-header.tsx` | 헤더에 "비공개 영역" 링크 추가 |
| `proxy.ts` | **수정하지 않았다.** `/private`는 `PUBLIC_PATHS`에 없으므로 비로그인 요청은 기존 규칙대로 `/login`으로 간다. 이 이동은 빠른 안내일 뿐이고, 실제 검사는 위 두 곳이 서버에서 다시 한다 |

기존 인증(`requireUser`, `getCurrentUser`, Supabase Auth 쿠키 세션)을 그대로 썼고, 인증을 우회하는 플래그나 하드코딩된 사용자는 없습니다.
이 인증은 **이메일·비밀번호**입니다. 패스키가 아닙니다. 가입이 열려 있으므로 가입해 이메일 확인을 마친 사람은 누구나 비공개 영역을 볼 수 있습니다. 이 한계는 화면에도 적어 두었습니다.

## 확인한 것

시험은 두 곳에서 했고, 증명하는 범위가 다릅니다.

- **개발 샌드박스(작성 시):** Google Fonts를 받을 수 없어서 **`app/layout.tsx`의 폰트 부분만 뺀 복사본**으로 빌드·실행했고, 실제 Supabase로는 로그인할 수 없어서 **가짜 Auth 서버**를 썼습니다. 이 시험은 "우리 코드가 Supabase Auth의 응답을 맞게 처리하는가"를 보여 줄 뿐, 실제 Supabase의 동작을 증명하지 않습니다.
- **사용자 로컬(2026-10-29):** 실제 `layout.tsx`, `.env.local`의 실제 Supabase, 이메일 확인을 마친 시험 계정으로 실행한 결과를 사용자가 전달했습니다. 아래 두 번째 표가 이것이며, 작성 쪽이 출력을 직접 보지는 않았고 전달받은 출력 기준입니다.

### 개발 샌드박스 (가짜 Auth)

| 시험 | 결과 |
|---|---|
| `npx tsc --noEmit` (`npx next typegen` 뒤) | 통과 |
| `npx eslint` | 경고·오류 없음 |

| `next build` (폰트 제외 복사본) | 통과. `/private`, `/api/private-items`는 요청 때 서버에서 만드는 동적 경로 |
| `node scripts/verify-private.mjs` (A: 비로그인, C: 빌드 산출물) | 16개 중 16개 통과 |
| 같은 스크립트, 유출 파일을 일부러 둔 폴더를 (C)에 지정한 대조 시험 | 실패(exit 1)로 잡힘 — 검사기가 실제로 유출을 잡는다 |
| 브라우저 시험 (Playwright, 가짜 Auth로 로그인한 세션) | 12개 중 12개 통과: 항목 3개 이상, "가상 데이터" 표시, 이메일 미표시, API 200, 비로그인은 `/login`으로 이동 |

(A)가 본 것: 비로그인·엉터리 토큰·엉터리 쿠키의 API 401, 쓰기 메서드 4xx, 비로그인 `/private`의 307 이동, 응답 본문·`/login` HTML에 비공개 항목 없음, 기존 `/`의 이동과 `/api/plans`의 401 유지.
(C)가 본 것: 브라우저로 내려가는 `.next/static` 파일 17개에 비공개 항목이 없음. 같은 항목이 서버 쪽 산출물에는 있음을 확인했다.

## 확인하지 못한 것

- **실제 브라우저에서 로그인한 상태의 `/private` 화면.** (B)는 Bearer 토큰으로 API만 본다. 쿠키 세션으로 화면이 그려지는 것, 가상 항목 4개와 "가상 데이터" 문구, 이메일 미표시는 개발 샌드박스의 가짜 Auth에서 헤드리스 Chromium으로만 봤다. 사람이 직접 보는 확인이 남아 있다.
- Vercel 배포본에서의 동작, 배포 URL의 쿠키·네트워크, 배포본 대상 `verify-private.mjs` 실행.
- `verify-api.mjs` 등 로그인이 필요한 기존 검증 스크립트의 재실행. (이번 변경은 기존 API 파일을 건드리지 않았다)

## 직접 확인하는 방법

1. **비로그인 (시크릿 창):** 배포 주소의 `/private`를 연다 → 로그인 화면으로 이동해야 한다. 페이지 소스 보기에 "별빛 일지", "가상 메모" 같은 글자가 없어야 한다.
2. **비로그인 API:** `curl -i https://<배포 주소>/api/private-items` → `401`, 본문은 `{"error":"로그인이 필요합니다."}`뿐이어야 한다.
3. **로그인:** 시험 계정으로 로그인 → 헤더의 "비공개 영역" → 가상 항목 4개와 "가상 데이터" 문구, 이메일이 보이지 않는 것을 확인한다.
4. **로그아웃 직후:** 뒤로 가기나 `/private` 직접 입력 → 다시 로그인 화면으로 가야 한다.
5. **스크립트:** `node scripts/verify-private.mjs https://<배포 주소>`. 시험 계정 환경변수를 주면 (B)도 실행된다.
